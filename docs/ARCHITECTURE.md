# LeafFS 技术文档

作者：ewq2526。

本文面向**接手或二次开发 LeafFS 代码的人**：讲清各层的职责、关键机制为什么这么设计、以及改动时该碰哪里。
使用与部署看 `../README.md`，版本变更看 `../CHANGELOG.md`，安卓端构建细节看 `../android/README.md`。

> 约定：本文描述**当前代码**的行为。凡是"只看代码看不出来"的设计理由，都写在对应小节里 ——
> 那些理由多数是踩坑换来的，动手删之前请先读一遍。

## 1. 总览

### 1.1 是什么

局域网文件分享 / 下载服务器：部署在局域网内一台机器上，同网络的其它设备用浏览器访问它的地址，
即可浏览、预览、上传、下载文件，**使用方不需要安装客户端**。

- 后端：Python 3.12，标准库 `http.server`（`ThreadingHTTPServer`）+ `websockets`，**不使用 Web 框架**。
- 前端：静态 HTML/CSS/JS，中英双份页面文件，**没有构建步骤**。
- 桌面形态：pywebview 内嵌窗口（Windows 上即 WebView2）。
- 安卓形态：Chaquopy 把整个 Python 服务端打进 APK，界面容器是 GeckoView。

### 1.2 三种运行形态

同一套 `leaffs/` 包同时服务三种运行方式，**源码只有一份**：

| 形态 | 入口 | 外壳 | 数据目录 |
|---|---|---|---|
| 源码运行（开发） | `python -m leaffs` | 内嵌窗口，失败则系统浏览器 | 项目根目录 |
| 打包运行（分发） | 可执行文件 | 内嵌窗口，失败则系统浏览器 | 主程序所在目录 |
| 安卓 | APK | GeckoView 容器 | App 私有目录 |

三者的差异集中在**入口装配**与**路径解析**两处，业务代码完全共用。
安卓端不复用桌面的启动函数（要避开内嵌窗口、证书提示页等桌面流程），而是自带一个编排入口。

### 1.3 端口

| 端口 | 用途 | 协议 |
|---|---|---|
| 8080 | 主站（页面与 API） | HTTP，或启用 TLS 后的 HTTPS |
| 8081 | WebSocket（文件列表、下载进度、推送） | ws，或启用 TLS 后的 wss |
| 8082 | 证书提示页 | 纯 HTTP，**仅启用 TLS 时提供** |

端口都可在配置里改。**证书提示页必须留在纯 HTTP**：它的存在意义就是在证书不被信任时还能被打开。

### 1.4 进程与线程模型

服务端是**多线程**模型，不是异步框架：

- **HTTP**：每连接一个线程。HTTP/1.1 keep-alive 下，一条连接会依次服务多个请求。
  连接有准入上限（整机与每 IP 两级），超限**直接拒绝、不排队**。
- **WebSocket**：独立端口、独立的 asyncio 事件循环，跑在自己的线程里；推送与它共用这个循环。
- **管理推送**：一个后台线程按固定节奏给订阅者推数据，**没有订阅者时不构建数据**。
- **看门狗**：一个后台线程，检测请求是否停滞，卡住时把全部线程的调用栈写入文件留证。
- **下载器**：`aria2c` 是**独立子进程**，服务端通过 RPC 与它通信；另有守护逻辑在它挂掉时自动重启。
- **安卓端**：另有前台服务（保活）与 GeckoView 容器，Python 侧仍是上面这套。

### 1.5 启动装配顺序

`leaffs/app.py` 的 `start_server()` 是**唯一装配点**，顺序有讲究：

1. 日志就绪 → 读配置 → 读账号 → **读回会话表** → 起会话清理；
2. 清理缩略图孤儿 + **清理上传临时目录**；
3. 建共享目录，记一条启动日志（共享目录、ffmpeg、aria2c 是否可用）；
4. 生成**本机一次性登录令牌**（覆盖上一份）；
5. 若启用 TLS：先构建 TLS 上下文，**失败就直接拒绝启动**；
6. 起证书提示页（仅 TLS 时）→ 起 HTTP → 起 WebSocket → 起管理推送 → 起看门狗；
7. 后台启动 `aria2c` 及其守护；
8. 打印启动横幅（含本机令牌链接）；
9. 打开桌面内嵌窗口；没有桌面环境时回退到系统浏览器，并让主线程存活。

几处**不能随意调换**的：

- **会话表必须在起 HTTP 之前读回**，否则最初几个请求看不到已有会话 —— 重启掉登录就是这么来的。
- **TLS 上下文必须在起 HTTP 之前构建，且构建失败不允许降级为明文**。这是刻意的安全策略：
  宁可不启动，也不在用户以为开着 HTTPS 的时候明文提供服务。
- **上传临时目录只在启动时清理**。运行期清理会把正在上传的文件删掉，而启动那一刻必然没有在途上传。

## 2. 模块地图

`leaffs/` 按**域**分包，一个包只做一件事。依赖方向总体单向：
`server` / `web` 依赖各域包，域包之间尽量不互相依赖；`paths` / `runtime_log` / `utils` 在最底层。

| 包 / 文件 | 职责 | 关键文件 |
|---|---|---|
| `app.py` | **启动装配**：读数据、起各线程、开窗口 | —— |
| `leaffs.py`、`__main__.py` | 入口垫片，指向 `app.py` | —— |
| `server/` | **传输层**：HTTP、WebSocket、TLS、推送、证书提示页、主机工具 | `handler.py`（HTTP 处理器与统一出口）、`ws.py`、`tls.py`、`push.py`、`cert_remind.py`、`hosts.py` |
| `auth/` | **账号与会话**：登录、限速、令牌、用户管理、自助接口 | `core.py`、`login_api.py`、`local_token.py`、`users_api.py`、`self_api.py` |
| `files/` | **文件**：上传下载、列表、搜索、统计、缩略图、路径与配额 | `core.py`、`api.py` |
| `share/` | **分享**：虚拟分享目录的映射、访问码闸门 | `mappings.py`、`access.py` |
| `config/` | **配置**：读写、校验、三层配置接口 | `core.py`、`api.py` |
| `dl/` | **下载器**：任务模型、aria2c 的 RPC 与看护 | `manager.py`、`dl_core.py`、`dl_api.py`、`dl_rpc.py` 等 |
| `web/` | **页面渲染**：静态资源、页面选择、主题注入、内容策略 | `render.py` |
| `web_page/` | **页面文件**（是资产不是代码）：`*.html` 与 `*.en.html` | —— |
| `utils/` | 通用工具（含全站 Cookie 解析口径） | `core.py`、`log.py` |
| 底层单文件 | `paths.py`（路径解析）、`runtime_log.py`（日志）、`watchdog.py`（卡死取证）、`ui_theme.py`（主题色） | —— |

### 2.1 "唯一实现"的收口点

改动时**优先改这些地方，不要在别处再写一份**：

| 收口点 | 位置 | 管什么 |
|---|---|---|
| 响应统一出口 | `server/handler.py` 的 `send_json` / `send_error` / `redirect` / `end_headers` | 状态码、正文定界、安全响应头、缓存头、页面内容策略 |
| 目录列表构建 | `files/api.py` 的 `build_listing()` | 列表的**唯一算法**，HTTP 与 WebSocket 共用（只"算"不"发"） |
| 临时内容判定 | `paths.py` 的 `is_upload_tmp_entry()` / `is_upload_tmp_relpath()` | 上传临时内容对所有读路径不可见 |
| 分享解锁判定 | `share/access.py` 的 `code_gate()` | "谁算已通过访问码" |
| Cookie 解析 | `utils/core.py` 的 `parse_cookies()` | 全站 Cookie 取值口径 |
| 主题实现 | `web_page/common/theme.js` | 全站主题色 |
| 内嵌窗口出站守卫 | `app.py` 的 `_install_webview_guard()` | 桌面端不允许访问外部地址 |

⚠️ 这些收口点是**踩出来的**，不是设计洁癖：

- 目录列表原先 HTTP 与 WebSocket **各写一份**，于是"公共分享目录在实时通道里凭空消失"成了一个真缺陷；
- 临时上传内容的判定原先**散在七个读取点**，漏掉一个就等于把它暴露出去；
- 响应头原先**每个处理器自己发**，于是有的响应没有缓存头、有的没有安全头。

**新增一个出口或读取点时，调用上面这些函数；另写一份必然漏。**

## 3. HTTP 请求处理

### 3.1 分发方式

HTTP 处理器是 `BaseHTTPRequestHandler` 的子类，`do_GET` / `do_POST` 按路径把请求分发给一组处理器。
两条贯穿全项目的惯例：

- **页面处理器自己判权限**，API 处理器只做转发。同一个域的页面与 API 是两种形状，别互相套用。
- **契约类检查放最外层，业务合法性放下层**。反例是真实踩过的：把"缺参数就报 400"写在业务层，
  结果外层先把请求拒了，那条精心写的 400 永远到不了。

### 3.2 统一出口

所有 HTTP 响应都要经过统一出口，它负责四件事：

| 出口 | 负责 |
|---|---|
| `send_json` | JSON 响应（状态码 + 正文定界） |
| `send_error` | 错误响应（统一拒绝口径） |
| `redirect` | 跳转（同样要带正文定界） |
| `end_headers`（覆写） | **兜底**：正文定界、安全响应头、缓存头、页面内容策略、`Connection` 头 |

几条规则：

- **正文定界**：HTTP/1.1 下每个响应都必须能自证边界（`Content-Length` 或分块），
  否则连接没法安全复用。统一出口会检查并在缺失时告警 —— 这是 keep-alive 敢开的前提。
- **缓存默认关闭**：没有显式声明缓存策略的响应，会被兜底补成 `no-store`。
  规则是"**默认不缓存，要缓存必须显式声明**"，例外只有两处：静态资源与缩略图。
- **安全响应头**由统一出口成批补上，并带幂等标记，避免手写响应重复发。
- **页面内容策略**只对 HTML 页面发，静态资源与 API 不发（见第 12 章）。

⚠️ **"所有响应"要先数清楚有几条路。** HTTP 主服务走上面四个函数，但：

- **WebSocket 握手那条不走它们** —— 它在 `ws.py` 里直接构造 HTTP 响应；
- **证书提示页也不走** —— `cert_remind.py` 有自己的处理器类。

改"所有响应"的公共行为时这三条都要过一遍。漏掉 WS 握手是踩过的坑。

### 3.3 连接复用（keep-alive）

服务端声明为 HTTP/1.1 并支持连接复用，因此**一条连接会依次服务多个请求**。带来四个必须做对的地方：

| 关注点 | 做法 | 不做会怎样 |
|---|---|---|
| **空闲回收** | 连接空闲时用较短的**空闲超时**（默认 15 秒，可配置）而不是读超时 | 浏览器挂着的空闲连接会一直占着服务端线程 |
| **每个请求重算预算** | 每个新请求开始时重置计时与超时 | 连接活得越久，超时预算越少，后面的请求莫名失败 |
| **补读** | 上一个请求没读完的正文，**必须补干净**才允许复用连接 | 残留字节被当成下一个请求的开头，两个请求串位 |
| **旧客户端** | HTTP/1.0 客户端一律按"用完即关"处理 | 老客户端等不到它期待的行为 |

另外，**分块方式提交的请求体被明确拒绝**，而不是被静默当成"没有正文" ——
静默丢弃等于让上传内容凭空消失。

### 3.4 连接准入

连接有两级上限：**整机**与**每 IP**。两者都在建立连接时判定，**超限直接拒绝、不排队** ——
排队会让攻击者用少量连接耗尽服务端资源。

读写都有超时兜底：单次读取有读超时，长时间没有进展的连接会被断开。

## 4. WebSocket 与推送

### 4.1 它承担什么

WebSocket 跑在**独立端口**，有自己的事件循环，承担三类工作：文件列表的实时获取与变更通知、
下载进度、管理页的实时数据。

⚠️ 于是**"读一次文件列表"有两条路**（HTTP 与 WebSocket）。这正是历史上出过缺陷的地方，见 4.3。

### 4.2 握手与消息

- **来源校验在握手之前**：来源（Origin / Host）不合法时，连接**根本不会建立**。
  放到握手之后再校验等于"先接受再判断"，中间那段窗口足够做坏事了。
- **消息有形状契约**：进业务分支之前先校验形状（字符串、字符串列表等）。
  不校验的后果不是报错，而是**静默错乱** —— 例如传进来一个字符串，被逐字符当成路径列表用。
- **畸形消息回明确应答、并保留连接**：帧级或信封级的问题回一条格式错误消息，
  **不按 WebSocket 协议关闭连接**。取舍是明确的：用户看到"页面忽然连不上"比看到一条错误提示糟糕得多。
- **订阅类消息不回应答是设计**：订阅只是登记，有事件时才推。没有应答不等于超时。

### 4.3 列表出口只有一条

目录列表有 HTTP 与 WebSocket 两条读取路径，但**构建算法只有一份**（第 2 章的收口点）：

- 它**只"算"不"发"**，返回结构化结果，由各自的传输层决定怎么送；
- 它固定按"规范化路径 → 拒临时内容 → 判权限 → 扫描 → 注入虚拟分享条目"的顺序执行。

⚠️ 这是硬约束，因为两条路各写一份时出过两个真缺陷：

- HTTP 那条会合并公共分享目录，WebSocket 那条不会 —— 表现为**做一次文件操作，公共分享目录就从列表里消失**；
- WebSocket 那条漏了对上传临时内容的拦截 —— 表现为**能点名列出正在上传的临时文件**。

第一个缺陷排查了很久，因为**前端优先走 WebSocket**、只有部分操作后才走 HTTP，
看起来像"有时才对"，很容易误判成前端缓存问题。

### 4.4 推送

推送与 WebSocket 共用同一个事件循环，按主题分几类：管理页实时数据、下载状态变化、
二维码登录事件、图库变更通知。

一条设计约束：**没有订阅者时不构建数据**。管理页的推送是定频的，
但绝大多数时间没人在看管理页，"先算完再发现没人要"是纯浪费。

## 5. 认证与会话

### 5.1 角色

三级：**普通用户 / 管理员 / 超级管理员**。角色决定两件事：能访问哪些路径、能改哪些配置。

超管有两处特殊，都是踩过坑之后改成的：

- **没有口令也能存在**：首次启动就是这个状态，唯一入口是本机一次性令牌；
- **按角色判定，不按用户名判定**：超管改名、或删掉 `admin` 另建一个超管之后，
  仍然要被认成超管。依赖"用户名是不是 `admin`"的写法曾经让真正的默认口令提醒**再也不会出现**。

### 5.2 口令

以慢哈希存储（PBKDF2-HMAC-SHA256），格式是"迭代次数、盐、摘要"三段，迭代次数与盐长可配置。
改动这两个参数**只影响新设与修改**，存量口令不会失效。

**默认口令的提醒按角色判定**：只要有任一超管还没设口令，页面就提示。

### 5.3 会话

- 会话**既在内存也在磁盘**：内存供快速查表，磁盘保证重启后登录状态还在。
  ⚠️ 会话文件等同于凭据 —— 删掉它等于把所有人登出，备份时要按敏感文件对待。
- 过期是**绝对过期，没有空闲超时**。这是刻意取舍：本项目定位是个人自建服务，
  频繁重登录的代价大于收益；要收回权限用下面的撤销手段。
- **撤销必须立即生效，且不能"重启后复活"**。登出、踢下线、改口令、删账号都要真正清掉会话记录，
  而不是只在内存里打个标记 —— 这是会话落盘之后必须额外守住的一条。
- Cookie 属性与服务性质对齐：不可被页面脚本读取，跨站请求受限。

### 5.4 登录限速

登录有多层限速，**每层的键不同**，这一点是关键：

- 只看来源 IP，会被"换 IP 就重置"绕过；
- 只看账号，会被"换个名字就重置"绕过；
- 所以两层都要有，另外还需要一层**跨账号的全局保护**来兜住分布式喷洒。

阈值与窗口都是常量，改动它们要连带看测试里钉住的口径。
触发限速时**要回明确的原因**，而不是统一回"用户名或密码错误"——
后者会让被锁住的合法用户以为是自己记错了口令。

⚠️ 已知取舍：**锁定期间正确的口令也会被拒**。这是防爆破的固有代价，不是缺陷。

### 5.5 本机一次性令牌

用于第一次进管理界面和忘记口令的场合：服务每次启动生成一个新令牌，
通过启动横幅里的链接带出，**只在环回地址可用、用一次即失效**。

- 令牌**没有查询接口**（设计如此：能查就等于能偷）；
- 候选值在进入比较之前先做**形状校验**，畸形输入按"不匹配"处理，不走比较逻辑；
- 令牌文件每次启动重写，用过即删。

### 5.6 二维码登录

一端展示二维码、另一端确认，完成登录。二维码会话的有效期很短、随机值熵足够大，
状态只有"等待 / 已确认 / 已过期"三态，**不含任何账号信息**。

轮询接口免认证，但输入空间不可枚举，因此不构成"探测某个会话存不存在"的面。

## 6. 权限模型

### 6.1 只有一个判定入口

路径 → 权限的判定收在一个函数里（`files/core.py` 的 `check_path_permission_core`），
**HTTP 与 WebSocket 共用**。规则可以概括成：

| 角色 | 能访问 |
|---|---|
| 超级管理员 / 管理员 | 全部 |
| 普通用户 | 自己的目录 + 公共目录 |
| 游客 | 公共目录（且必须开着游客模式） |

「公共目录下的分享区」是唯一的例外，见 6.3。

两条配套约定：

- **判定抛异常 = 拒绝**。实现上必须先留痕再拒绝 —— 既不能把异常读成"有权限"，
  也不能静默当成无权（否则问题永远查不出来）。
- **还有第二道防线**：所有拼接出来的绝对路径都要再校验一次"确实落在共享根内"。
  第一道判定管的是"这个人该不该看"，第二道管的是"这个路径会不会跑出去"，两者不可互相替代。

### 6.2 路径处理

相对路径先归一化，再进判定。归一化里有三个**必须**，每条都对应一个真实缺陷：

- **`..` 必须在 `normpath` 之前检查** —— `normpath` 会先把它解析掉，之后再查就查不到了；
- **必须挡盘符** —— `normpath` 不处理盘符，而 `join(共享根, 'C:/x')` 在 Windows 上**直接返回 `C:/x`**，
  等于跳出共享根；
- **空路径要显式拦** —— 归一化后空串是"合法"的，而 `join(共享根, '')` 正好**就是共享根本身**。

最后一条曾经造成过最严重的缺陷：删除接口收到空路径时，目标是"路径本身"，
于是**整个共享根被递归删光，还回了成功**。删除这类"对目标路径本身做动作"的接口必须显式拦空值；
上传和新建目录的空路径含义不同（父目录 = 共享根），且有角色收敛，性质不一样。

单个文件/目录名另有一套净化规则（拒绝分隔符、控制字符、Windows 保留设备名、超长等）。
上传文件夹时浏览器会带多段相对路径，逐段套用同一套规则，并限制总段数。

### 6.3 公共分享保留区

`public/shares` 是**虚拟区**：磁盘上不放实体，只有映射表登记。它必须设防，因为任何能写公共目录的角色
都可以在那儿建出一个**实体**目录，而"列表按磁盘条目优先、下载按磁盘路径"——
实体目录里的文件就**绕过了分享码**。

所以有三道防线：权限判定里非管理员一律拒绝该区（管理员放行是刻意留的清理通道）、
列表合并时剔除磁盘上的同名实体条目、登记分享时禁止把源指向该区。

### 6.4 拒绝口径

身份与权限类拒绝统一成**同一个状态码**，不区分"未登录"和"无权"。
理由很直接：区分开就是一个"这个资源存不存在 / 你有没有资格"的探测口。
页面型请求另有一套（未登录跳登录页，无权才拒绝）。

⚠️ 改"所有响应"的口径时，记住响应出口有三条路（第 3.2 节），别只改 HTTP 那条。

## 7. 文件与上传

### 7.1 读写路径

**读**：列目录、下载（支持断点续传）、原始内容/预览、缩略图、打包下载、搜索、统计。

**写**：上传、删除、新建目录。

两类路径都必须经过权限判定，并且都必须在第 4.3 节那条**唯一列表出口**与第 7.4 节那条
**唯一临时内容判定**之内。

### 7.2 上传

上传是流式的，**没有"先收到内存再写盘"这一步**：

1. 校验请求类型与**客户端声明的大小**（此时只做预检，**不记账**）；
2. 判角色、判路径、判写权限；配额用声明值做一次快速预检；
3. 流式解析 multipart，边读边写进**临时文件**；
4. 收全之后**原子落位**（同盘改名），换名成功那一刻文件才算存在。

几个关键点：

- **临时文件放在共享根下的专用目录里**，命名用"线程号 + 纳秒时间戳"，天然不撞；
- **中断的判据是"有没有读到结束边界"**，不是"连接是不是正常关闭" ——
  格式完好的请求体必然以结束边界收尾。判据选错时，半截数据会被当成完整文件落位、还报成功；
- **任何异常都删掉临时文件**，不留下半截；
- **同名冲突按角色区别对待**：游客**绝不覆盖**（自动改名承接），其他角色保持原子覆盖语义。

### 7.3 配额记账

配额按**实际读入的字节**记账，不按请求声明的长度。这一条是被攻破之后改的：

> 原先按声明的长度预留，于是"声明一个很大的值、正文却不发完"就能在请求存活期间把配额**虚拟占满**，
> 期间所有人的上传全被拒。现在数据没真的传上来，一个字节也占不到。

配套的三条：

- 记账挂在**唯一的数据读取点**上，因此"被跳过、被拒绝的片段"同样计入 —— 它们也是真读进来的；
- 预留只在**请求进行期间**有意义（防的是"检查完配额、还没写盘"这段窗口里的并发超卖），
  请求结束必须结算；
- **结算顺序不能反**：先让目录大小统计失效、再结算预留。反了就会把同一批字节算两遍。

⚠️ 取配置失败时**绝不能退化成"不限"**。把"读配置出错"读成"用户要求不限"是这类代码的经典陷阱，
本项目在几处上限上都显式选择了"宁可让异常打断本次操作"。

### 7.4 临时内容的可见性

上传中的临时内容必须对所有读路径不可见。判定**只有一份**（第 2 章的收口点），
但**调用点有十来个**：列表（扫描层与点名进入是两处）、搜索、下载、原始内容、缩略图、
打包（基准、单项、目录递归）。

⚠️ 两个容易做错的地方：

- **"不列出它"挡不住"直接走进去"** —— 列表层跳过不够，点名访问那条路必须单独拦；
- **拦截回 404，不回 403**。语义是"没有这个资源"，与权限无关；
  回 403 等于承认"这儿本来有东西"。

### 7.5 打包下载

两种模式，取舍写在配置项旁边：

| 模式 | 做法 | 代价 |
|---|---|---|
| **全流式**（默认） | 边压边发，输出流**刻意不可随机访问**，让压缩库改用流式写法 | **没有总长度**，客户端看不到进度与总大小 |
| 先打包后发 | 先打到**内存/临时文件**（小包留内存，大包自动落盘），再发 | 大包会占临时磁盘（可能写满），首字节更慢 |

全流式的实现细节有一条**正确性**要求：正文写完必须显式收尾并刷新，
否则客户端会一直等下一个数据块。这不是性能优化。

上限控制在多处：URL 长度、参数长度、条目数量上限。
**一个都没打包成功时统一回 404**，不再回一个 200 的空包 —— 那是假成功；
而且此时**不区分"无权"与"不存在"**，区分开就是权限探测口。

## 8. 分享

### 8.1 模型：登记引用，不复制文件

分享**不是复制**：文件被分享之后，磁盘上不产生副本、也不产生链接，只是**登记了一条映射** ——
"这个虚拟路径指向那个源文件"。由此推出三件事：

- 源文件删除或移走，分享自然失效，不需要额外清理；
- 分享不占额外空间，也不改变配额口径；
- 映射表会落盘，并设有**总量上限与单用户上限**（防失控增长）。

虚拟分享目录固定在"公共目录下的分享区"（`public/shares/<用户名>/`），
它**只由映射表产生**，磁盘上不放实体 —— 这是下一节所有防线的前提。

发布时会做几项校验：源路径必须落在共享根内、必须已经是文件、不允许把分享区里的东西再分享一次。
虚拟文件名与磁盘条目**自动避让**，保证"磁盘 + 虚拟"两层视图不出现重名。

### 8.2 合并进列表：唯一实现 + 唯一解锁判定

目录列表的收口点（第 4.3 节）在这件事上有个配套函数：把虚拟条目合并进列表结果。
它**只有一处实现**，也只有一处调用（在 `build_listing` 内部），因此 HTTP 与 WebSocket
两条路拿到的是同一个视图。

它接收一个"**是否已解锁**"的回调：

- 回调返回"未解锁"的分享者，其虚拟条目**一条都不合并** —— 连文件夹本身都不出现，
  统计也不计入；
- 理由：**文件名、大小、修改时间本身就是信息**，不能让人白看列表；
- 第三层未解锁时给的是**空列表，而不是拒绝** —— 拒绝等于告诉对方"这儿本来有东西"。

这个回调**唯一实现在 `share/access.py` 的 `code_gate()`**，`ws.py` 不另写一份。
⚠️ 这一条是硬要求：WebSocket 的列表也要按分享码过滤，不过滤等于把设了码的分享
**白送给任何连得上 WS 的人**；而 WS 侧没有 HTTP handler，所以判定被刻意做成
"不依赖 handler 的版本" —— 否则两份实现迟早漂移。

### 8.3 公共分享保留区

分享区是虚拟的，磁盘上不放实体。这件事必须**设防**，因为任何能写公共目录的角色
都可以在那儿建出一个**实体**目录，而"列表按磁盘条目优先、下载按磁盘路径"——
实体目录里的文件就绕过了访问码。

所以有三道防线：权限判定里非管理员一律拒绝该区（管理员放行是刻意留的清理通道）、
列表合并时剔除磁盘上的同名实体条目、登记分享时禁止把源指向该区。

### 8.4 访问码

访问码闸门要同时守住"**列目录**"和"**取内容**"两类口子 —— 只守后者会泄露文件名、
大小与时间。目前经过闸门的内容类出口有：下载、原始内容/预览、缩略图、打包下载、
访客页数据接口。

几个设计要点：

- **哈希用慢哈希**（与登录口令同一套参数与格式），不是单轮哈希。
  分享码下限只有 6 位，单轮哈希一旦映射表泄露就能离线秒破 —— 那时**在线的 IP 锁与
  全局锁全部归零**；
- 旧格式的哈希仍要能校验通过，并在**第一次输对码时**自动升级为新格式。
  ⚠️ 改这块**别把旧格式分支删了**，那会让所有已存在的分享码一次性失效；
- **校验通过才允许写盘升级** —— 错误码绝不触发任何写入，否则就给了"用错误码探测"的写副作用；
- 慢哈希不能在持锁时计算（那把锁不可重入）。一律"**锁内取值、出锁计算**"；
  升级写盘要重新进锁并复核期间没被并发改过。

**授权票据**：通过验证后发的凭据是**不透明随机值**（约 192 位），服务端记"谁 + 何时过期"。

⚠️ 票据**不能是"码的哈希"**：那个值可以由码推算出来 —— 攻击者离线枚举候选码、算出哈希、
自己写一个同名 Cookie 就能下载，**全程不经过输码接口，IP 锁与全局锁一点都拦不到**。
同理，过期必须**由服务端判定**，浏览器那边的过期时间只是顺手清 Cookie 用的。

### 8.5 防爆破

两层锁，作用范围不同：

- **按来源 IP**：当日累计错码到阈值即锁；
- **全局**：滑动窗口内的错码数达标**且来自至少两个不同来源**才触发。

⚠️ 第二条里"至少两个来源"不是可选项。不加它，**任何匿名者错五次码就能把别人的分享
对所有人锁死**，而且每过一个窗口再来一次还能无限顺延 —— 那是现成的拒绝服务手段。

跨日重置有两个踩过的坑，都在注释里写着：**不要清掉全局锁时间戳**（它是绝对时间戳、
自带到期判定，清了会让攻击者触发的锁跨过零点自动解除）；**不要清掉整张用户表**
（那会把分享码本身一起清掉，表现为"过了一天，访问码就再也输不对"）。

分享码本身**不分自然日**，跨天也要加载回来；按天归零的只有计数与锁。

映射表还会**按文件指纹决定要不要重载** —— 因为同一份数据根可能被本进程之外的东西改
（另一个实例、外部备份还原、手工编辑）。用"加载一次就用到死"的写法会一直用旧值、
而且不会自愈，只有重启才更新。指纹**刻意不用 inode**：本模块写入是"写临时文件再原子替换"，
每次替换 inode 都变，拿它当指纹会退化成"每次都重载"。

### 8.6 删用户时的级联

按用户名持久化的东西**只有两处**需要清：映射表里"谁分享的"条目，以及访问码表里
该用户的全部记录（码哈希、错误计数、两类锁、票据）。

⚠️ 顺序口径：**先归档家目录 → 再清分享数据 → 最后删账号与会话**。理由是清理由此不可逆但
危害小（用户重设码即可），而"账号删了、码还在"会让**重建的同名账号继承旧码** ——
分享页仍要求输码，而没人知道那个码。

### 8.7 服务器挂载区（`mounts/`，本机路径映射）

映射表支持第二种来源：**服务器本机的绝对路径** —— 把本机上的一个目录（或单个文件）
挂出来，**不复制任何东西**。它与普通分享**并列**，不是分享区的一部分：

```
shared_files/                 ← 共享根（数据根）
├── users/<用户名>/            ← 各用户私有
├── public/                   ← 公共目录
│   └── shares/<用户名>/<名字>  ← 普通分享（src）：按用户分、有分享码
└── mounts/<名字>              ← 服务器挂载（fs）：不分用户、没有分享码这一层
```

**两种来源、两种逻辑**：

| | 普通分享（`src`） | 服务器挂载（`fs`） |
|---|---|---|
| 源 | 共享根内的相对路径 | 服务器本机绝对路径 |
| 形态 | 只能是文件 | 目录或文件 |
| 归属 | **按用户分**（`shares/<用户名>/`） | **不分用户**（这台服务器的东西） |
| 建立入口 | 浏览页勾选 → 分享 | **只有服务端本机**（本机令牌会话） |
| 访问权限 | 各自的分享码 | 与**公共目录一个级别**（能看 `public` 的就能看它） |
| 大小 | 走正常那套（有缓存） | 不参与公共目录统计（见下） |

要点：

- **名字就是路径的投影**：条目名取自源路径自己的名字（`E:\电影` → `mounts/电影`），
  不起别名。理由：挂载只有服务端本机能做 —— 他看到的名字就该是他在资源管理器里看到的
  那个。同名撞车**直接拒**，不自动改名（改名会让名字与实际指向对不上）；
- **解析**：挂载目录**内部**的文件不在表里逐条登记，靠"**虚拟前缀 + 余部**"拼出来，
  取最长前缀（嵌套挂载以更具体的那条为准）；拼完仍按**登记的那个根**判越界 ——
  **绝不拿请求里的字符串去拼绝对路径**。这条解析只有一处实现（第 4.3 节的收口点），
  读路径与写路径都走它；
- **只读**：挂载来源在解析结果里带"只读"位，**所有写入口据此拒绝** ——
  删除（HTTP 与 WebSocket 各有一处实现）、建目录、上传。理由很直接：
  挂进来的是使用者自己的系统目录，一次误删就是真的删了系统文件；
- **鉴权**：挂载接口只认**本机一次性令牌建立的会话**，也就是"操作者人就坐在服务端
  这台机器前"。远程登录的管理员同样拒绝 —— 能挂本机路径等于能读这台机器的任意文件，
  这个能力不跟账号走，只跟"人在机器前"走。令牌一次性、用过即删，所以判定落在它的
  产物（那条会话）上，而那条会话的来源是环回；
- **大小口径**：`mounts` 目录本身**报 0**、不参与目录大小统计（它是映射出来的）；
  **进了挂载目录之后**，条目按真实大小报 —— 那一层走服务端既有的目录统计。
  `public` 下那个 `shares` 目录同样报 0：分享区全是虚拟条目，不参与公共目录统计；
- **不跟随**：搜索与递归扫描**都不进挂载区**；
- **失效**：系统里的文件被删掉或移走，条目照旧在、显示为"源已不存在"，
  与普通分享同一套行为 —— 登记的是引用，不是副本。

⚠️ **尚未做**（下一步）：挂载区自己的**分享码**（在服务端界面设，独立于 share）、
以及把码的粒度从"每个用户一个"改成"**每条分享一个**"（内部按**随机标签**索引，
码对本人与管理员**可读回**）。

## 9. 配置体系

### 9.1 三层，对应不同权限

| 层 | 页面 | 谁能改 | 管什么 |
|---|---|---|---|
| **基础** | 管理页 | 管理员 / 超管 | 游客模式、配额、限速、并发 |
| **高级** | 高级配置 | 管理员（个别项仅超管） | 端口、TLS、上传与预览上限、缓存、打包方式 |
| **深度** | 深度配置 | 管理员（**部分字段仅超管**） | 口令哈希参数、会话有效期、连接与超时、缩略图、日志开关、访问控制 |

分层的实际意义是**权限分层**：深度配置里有几个字段能削弱安全（口令迭代次数、会话有效期、
访问日志开关、证书信任相关），所以**只有超管能改**，普通管理员提交这些字段会**整单被拒**。
否则"能改日志开关"就等于"能抹掉自己的痕迹"。

几处**必须守住的特殊约束**：

- 关闭 TLS 需要显式确认参数，否则拒绝 —— 明文与加密之间不该是"点一下就过去"的差别；
- 端口之间必须互不相同，也不能占用证书提示页的端口；
- 连接总数上限不能设得太小（见 9.4）。

### 9.2 文件与敏感性

| 文件 | 内容 | 敏感性 |
|---|---|---|
| `server_config.json` | 全部运行参数（另有一份载入钳制时的备份） | 一般 |
| `users.json` | 账号、口令哈希、角色、配额、界面语言偏好 | **高** |
| `sessions.json` | 会话表（**内容等于凭据**） | **高** |
| `share_access.json` | 分享码哈希、票据、防爆破计数 | **高** |
| `share_mappings.json` | 分享映射 | 一般 |
| `downloader_config.json` | 下载器独立配置 | 一般 |
| `local_token.txt` | 本机一次性令牌（每次启动重写、用后即删） | **高** |
| `selfsigned.crt` / `.key` | 自动生成的服务器证书 | 私钥敏感 |

⚠️ 标"高"的几个都在配置目录下，**备份与拷贝时按凭据对待**：会话文件删掉等于把所有人登出；
访问码表泄露等于分享码可被离线破解。

配置目录里出现清单之外的 JSON，基本就是旧版本遗留 —— 先按这个思路查，别急着当新问题分析。

### 9.3 默认值只有一处

默认值定义在**配置模块的模块级常量**里，加载时逐键 `get(键, 默认值)` 与之对齐。
其它模块里的同类常量（如认证模块的迭代次数、会话有效期）在加载后会被配置值**覆盖**。

⇒ **改默认值就改配置模块那一处**；改别处的常量然后期待它生效是无效的。

### 9.4 校验：拒绝，而不是静默钳制

写入时的规则很硬，每条都对应一个真实毛病：

- **未知键整单拒绝** —— 原先是"未知键不进任何分支 → 什么都没改 → 却回成功"，
  用户以为改上了；
- **越界拒绝，不钳制** —— 钳制的表现是"用户提交 0、系统悄悄存成别的值"，与前一条同类；
- **布尔键只接受真布尔值**；数字键收到布尔值或非有限浮点直接拒；
- **有些键有语义下限**，不只是数值范围：例如连接总数下限若设成 1，服务会**自锁** ——
  连"改回来"的请求都抢不到连接槽，只能去改文件再重启。

写入还必须**读-改-写**：先读盘上的内容，**只覆盖自己管的键**，其余原样保留。
整份重建等于替用户重写配置文件，会把不认识的键抹掉。

写盘是"临时文件 + 原子替换"，失败要**返回失败并如实回给用户** ——
回一个"成功"但只在内存里生效，是骗人。

### 9.5 载入时的钳制要留痕

加载时会把明显不合法的值钳到边界内，但**钳制这个动作本身必须被记录下来**：

- 与写入共用同一份"受管键"清单；
- 比较的是**盘上的原值**，不是归一后的值 —— 否则 `"false"`、`"8082"` 这类
  "语义等价、类型不对"的值永远不会被修正；
- 发现漂移时先备份，再**只把被钳制的那几个键**写回，绝不整份重写；
- 只有文件根本不存在（首次启动）时才整份写入。

### 9.6 生效时机

**改配置不等于改行为**，这是最容易被忽略的一条：

| 生效方式 | 例子 |
|---|---|
| **保存即生效** | 口令哈希参数、会话有效期、缓存与防抖、连接总数上限、游客模式与配额 |
| **重启才生效** | 端口、证书提示页端口、TLS 开关 |
| **随取随用** | 上传/预览上限等在处理请求时读取的键 |

⚠️ TLS 是"重启 + 单例缓存"双重原因：TLS 上下文在进程内**只构建一次**，
所以**换证书也必须重启**。

⚠️ 界面文案是"部分参数重启后完全生效"，但**具体哪些键需要重启并没有逐条标注**。
改动配置相关代码时，请顺手确认并更新这句文案 —— 它现在是用户唯一的提示。

## 10. 下载器

### 10.1 任务类型与分派

支持四类：**HTTP/HTTPS 直链、m3u8 流、种子文件、磁力链接**。
类型识别按固定顺序判定（磁力 → 种子 → m3u8 → 直链），识别不出来的按直链处理；
电驴（ed2k）明确不支持并直接报错。

四类的实现各自独立，但**只有直链是自己下载的** —— 磁力、种子、m3u8 都交给外部
`aria2c` 进程，通过 RPC 指挥。

### 10.2 数据模型与状态

一个任务持有：标识、来源 URL、保存目录、类型、归属用户、进度与统计字段
（已下载、总量、速度、文件名、连接数、做种数、对等数、上传速度），以及分阶段信息
（磁力会先经历"取元数据"阶段再进入"取文件"阶段）。

状态迁移：`等待 → 下载中 → 完成 / 部分完成 / 失败 / 已暂停 / 已取消`。

- **"部分完成"是终态**（目前没有后续的合并/续传流程），所以不允许把片段残骸留在临时目录里；
- 给前端的是**白名单字段**：原始参数与内部标记不导出；
- 任务完成会**顺带失效目录缓存** —— 不然新文件既不进统计、也不推送
  （推送本来就挂在缓存失效的钩子上）。

### 10.3 aria2c 的启动与看护

- 可执行文件优先取随包的那份，取不到再试 PATH；
- 启动前**每次生成随机 RPC 密钥** —— 本机其它进程猜不出，也就调不动 RPC；
- 启动是**幂等 + 双检**的（后台启动线程与首个下载任务可能同时到达）；
- 就绪判定靠**真实握手轮询**，不是固定 sleep，不拖慢服务启动；
- 守护线程按周期检查：进程已退出则自动重启；进程活着但长时间连不上也重启；
- RPC 客户端发现密钥变了会**自动重建**（每次重启都换密钥）。

⚠️ 停止它要三种手段依次尝试（按进程树、按镜像名、直接终止），单独一种都可能漏。
另有控制台事件与退出钩子两条兜底路径，保证服务被强杀时不留下孤儿进程。

### 10.4 对外部目标的限制

这是下载器里最需要小心的部分 —— 它是**唯一由服务端主动发起出站请求**的功能。

判定方式：**解析出全部 IP，逐 IP 判定，任一个不合格就整体拒绝**
（字面量 IP 走快路径、不触网）。默认只允许公网地址；**即使打开"允许私网目标"，
回环、链路本地（含云元数据地址段）、保留段与运营商共享地址段依然永不放行**。

⚠️ 光校验第一跳不够，**重定向的每一跳都要校验**，所以：

| 路径 | 校验点 |
|---|---|
| httpx | 挂**请求钩子** —— 每一跳、每个最终请求发出前都过一遍 |
| urllib | 换成**安全重定向处理器** |
| m3u8 | 入口 URL + **重定向后的最终 URL** + 拼出来的**每一个分片** |
| 远程种子 | **受控预拉取**（带字节上限，双检），不把 http 链接交给 aria2 自拉 |
| 本地种子 | 只允许来自我们自己的临时目录（白名单判定，不是黑名单） |

其它限制：tracker 只从**白名单主机 + https** 拉取，并有行数上限 ——
防的是"配置被改成内网地址后让本模块去拉"；单文件大小上限在**三个位置**检查
（开始前、响应头、**流式实读累计**），只信 `Content-Length` 会被"服务器谎报或不给"绕过。

目标地址与种子里记录的路径都要过校验：种子内部的文件路径若含绝对路径、`..`
或盘符，**整体拒绝**。

### 10.5 门禁与配额

- **配置读写只有管理员**。这份配置不只是"并发数/限速"，还含"能否下载私网目标"
  与"DHT 是否对外暴露"这类**策略信息**；前端在同一处一并修好 ——
  非管理员的下载器页**不显示设置区、也不去拉配置**；
- **任务归属**：管理员看全部，其他人只看自己的；游客按**来源 IP** 隔离，
  不同 IP 的游客互相看不到对方的任务；
- **三档上限**：全池总数、每用户任务数、每用户同时下载数（0 或负值表示该维度不限）。
  判定在**入池时持锁二次确认**，保证原子性；
- 超龄清理只删**已到终态且超过保留期**的任务。

### 10.6 删除语义

⚠️ **绝不递归删目录**。删除任务时只删"该任务实际产出的文件"：

- **直链**：只删文件名本身与它的 `.tmp`（防御性地只取单文件名）；
- **磁力 / 种子**：本地**不删** —— 文件由 aria2 管理，删交给 RPC 的 remove 或用户自行处理；
- **m3u8**：只删结果里记录的路径，且规范化后必须落在保存目录之下；
- 断点续传的控制文件按"已知文件名"**精确拼接**删除，**不做目录级通配删除** ——
  那会误删其它任务或其它用户的控制文件。

**取消任务只停任务、不删任何文件**：文件语义归删除接口，两件事分开。

## 11. 页面渲染与多语言

### 11.1 没有构建步骤

页面是**运行时读盘下发**的：`web_page/` 下的 HTML/CSS/JS 原文件直接返回，
没有打包、没有编译、没有模板引擎。两个必须记住的后果：

- **下发的文件里写什么，用户就能看到什么** —— HTML/JS/CSS 的注释会被原样发给访客。
  内部路径、文件名、服务端机制说明**要写进 Python 文件的 docstring**，
  不要写进页面注释（有测试盯着这条）；
- **占位符替换是纯字符串替换，没有任何"没替换就报错"的机制** —— 漏一个，
  页面就把 `__XXX__` 原样显示给用户。所以有两道自动闸：静态查"有没有替换代码"，
  动态查"渲染出来的页面里还有没有残留"。

⚠️ 静态资源走的是**原文件、不做任何替换**。这是它能安全启用条件请求（第 15 章）的前提：
同一个 URL 对所有用户内容完全相同，所以"没变就回 304"不会串味。
**按会话注入的页面是另一条路**，它们因人而异、始终不可缓存 —— 不要顺手也给它们加验证器。

### 11.2 双语：同一目录放两份文件

多语言的做法是**直写英文页面文件**（同名 `.en.html`），不是运行时词典：
请求进来时按语言判定要不要换英文版，**英文文件不存在就回退中文版**，
读取失败也静默回退（不让一个翻译文件把页面搞崩）。

**语言判定顺序**：① 语言 cookie 的显式选择 → ② 已登录账号保存在服务端的偏好 → ③ 回退中文。

⚠️ 第 ② 条是为了**软件自带的窗口**：那是无痕会话、cookie 存不住，
只能靠服务端的账号偏好恢复上次的选择。游客与匿名没有账号偏好，走第 ③ 条。

### 11.3 主题色

主题是**一体的**（亮暗 + 主色），且**只看客户端本地的 cookie**，服务端不存储、账号里也没有。
服务端读 cookie 只是为了**首屏就渲染成对的配色** —— 避免先出来一个默认色再被 JS 改掉。

⚠️ 主题按钮原先在二十多个静态页里各抄一份，连初始文案都各写各的（英文页里写成中文词）。
现在是**一份实现 + 一个占位符**。

### 11.4 注入的地址与身份

服务端注入三类值，每一类都有踩点：

| 注入项 | 为什么要注入 |
|---|---|
| **WS 端口** | 前端要连实时通道，而端口可配置 |
| **服务器基址** | 分享页要给别人的是**局域网地址**，而网页自己是从回环地址打开的（桌面窗口是 localhost、安卓是 127.0.0.1）—— 用 `location.origin` 拼出来的链接**别人打不开** |
| **"有没有可用局域网"** | 前端据此提示"无可用局域网" |
| **当前用户名与角色** | 页面据此显示与隐藏功能，不让前端猜 |

⚠️ 两个占位符名称**刻意不与 JS 全局属性名相同** —— 否则全局替换会把属性赋值也一起换坏。

⚠️ 注入的基址来自 `Host` 请求头，属**不可信输入**：拼进 HTML 属性之前必须先校验它是不是
合法主机名。DNS rebinding 场景下 Host 归攻击者控制，原样拼进去就能闭合属性、注入标签。

⚠️ 注入值要按**输出上下文**转义：文本位置与属性位置用的转义不同。
把文本转义用在属性位置曾经造成过存储型 XSS（普通用户可借此影响到管理员）。
现在的规则是"属性上下文单独有一套转义"，并有测试钉住。

## 12. 页面策略与外部访问封锁

### 12.1 为什么要做成多层

用户的要求是"**在我们软件内不能访问外部**"。这不是一个开关，而是**几层独立的防线** ——
任何单独一层都不够：

| 层 | 管什么 | 由谁执行 |
|---|---|---|
| **内容策略（CSP）** | 页面里的子资源、脚本、连接 | 浏览器 |
| **导航白名单** | 页面跳转、新窗口 | 客户端内核 |
| **网络层拦截** | 一切非本机请求 | 客户端内核 |
| **内联渲染限制** | 用户文件里的 HTML/SVG 不被当页面渲染 | 服务端 |

分层的价值在**覆盖面不同**：CSP 由浏览器执行，所以桌面、安卓、任何浏览器**一起生效**，
不依赖客户端实现；而导航白名单只管导航，管不到子资源。

### 12.2 页面内容策略

页面响应带一条 CSP，把子资源**锁在同源**：`default-src 'self'`；
`connect-src` 除了 `'self'` 还**动态**带上自己的 WS 地址；`img-src` 补 `data:` 与 `blob:`
（缩略图与二维码可能内联）；留 `'unsafe-inline'`（页面里内联样式与内联脚本用得多）。

⚠️ **WS 那一项必须动态带，而且 `ws`/`wss` 都给**：前端连的是**自己另一个端口**的 WS，
`'self'` 不覆盖它 —— 漏了会把下载器的实时进度**静默**打断（不报错、只是不动）。

⚠️ 拼进响应头之前 **`Host` 必须净化**：CSP 是拼字符串发出去的，中间混进换行就是**头注入**。
净化只放行两种形状（方括号 IPv6、字母数字点连字符），端口一律丢弃 ——
WS 端口我们自己知道，不用客户端告诉我们。

**由谁发**：走统一出口（第 3.2 节）按 `Content-Type` 自动补，**不手工在各页面加**。
发 HTML 的地方不止一处，手工点必漏一处，而漏掉的那处就是缺口。
已有显式 CSP 的响应（静态资源按 mime、JSON、文件流）**不被覆盖**。

规则的依据是**查过页面实际用法**的，不是照抄模板：页面里没有 `<video>/<audio>/<iframe>`，
所以不需要 media-src / frame-src；也正因为查过，内联样式与内联脚本必须放行。

### 12.3 桌面端的出站封锁

内嵌窗口上挂**三层**拦截：

1. **导航层**：非本机地址的导航直接取消 —— **导航根本不发生**；
2. **网络层**：非本机请求直接构造一个空响应。实测这是**真的没发包**，不是发了再丢；
3. **新窗口层**：先摘掉外壳框架自己的处理（它默认会把链接**甩给系统浏览器**，
   等于我们主动把外链放出去），再接管为"什么都不做"。

⚠️ 三层都要，因为覆盖面不同：**导航层拦不住编程式的加载**；而拦截导航本身
**也会产生一次资源请求**，得靠网络层兜住。

⚠️ 实现依赖"能拿到内核的原生事件"，所以**升级外壳框架时必须回归这三层**。
历史上用过"定时检查当前地址"的写法 —— 那是"跳走之后再拉回来"，站外页面至少有几百毫秒的
加载窗口；现在是**零窗口**。

⚠️ 别再去试"改 DNS 解析"那一类启动参数：实测**被内核过滤**，加了照样能打开外部站点，
是**假保护**。这类"看起来生效了"的假保护比不做更危险，因为它让人以为已经安全了。

### 12.4 安卓端的封锁

安卓侧分两块，**导航**与**子资源**各管一头：

- **导航白名单**：容器判定加载请求，只允许本机地址；
- **子资源**：由**内置浏览器扩展**在网络层拦截，只放行本机地址。

⚠️ 子资源不走导航回调，所以"管住导航"**不等于**"管住子资源" —— 这是两层分开的原因。

⚠️ 扩展的判定口径**必须与客户端本体的白名单一致**，否则会出现"导航允许、子资源被拦"
这种极难排查的怪事（有测试钉住这条一致性）。另有两条配套：**解析失败按"不可信"处理**
（宁可拦错、不可放过）；**内容脚本注入不了 `data:` 页面**，所以权限页与错误页要自带样式，
不能依赖注入。

### 12.5 服务端侧的配套

用户上传的 HTML/SVG 等脚本类文件**不被内联执行**：预览时按纯文本或下载返回。
它挡的是"把恶意页面放进共享目录、再诱导别人点开"。

⚠️ 这只是纵深防御的一层，**不要指望它当唯一防线** —— 页面上也写着"请勿依赖此机制
存放并分享可执行或含脚本内容"。

## 13. 安卓端

### 13.1 形态

安卓版把**整个服务端**打进 APK：App 启动后，同一 WiFi 或热点下的其它设备用浏览器访问
手机地址即可使用 —— 与桌面版是**同一套服务端与网页**。

- Python 运行时由打包框架（Chaquopy）提供。**源码的单一事实来源是仓库根的 `leaffs/`**：
  构建时由 Gradle 同步任务拷进去，**桌面代码零改动、不维护两份拷贝**；
- 界面容器是 **GeckoView**，不是系统 WebView —— 换容器等于**换网络栈的控制权**；
- 只有 64 位；按 ABI 分 flavor（真机 arm64 / 模拟器 x86），**选错会构建失败**。

### 13.2 入口与桌面的差异

安卓**不复用**桌面的启动函数，而是自带一个编排入口。差异都在"桌面有、安卓没有"的东西上：

| 项 | 桌面 | 安卓 |
|---|---|---|
| 内嵌窗口 / 浏览器回退 | 有 | 无（用自带容器） |
| 下载器守护进程 | 启动 | **不启动**（没有 aria2c，靠代码自身降级） |
| 主线程 | 被窗口阻塞 | 不阻塞 |
| 数据根 | 项目根 / 主程序目录 | App 私有目录 |

启动前还会**预检端口是否空闲**。⚠️ 预检必须带 `SO_REUSEADDR`，否则 TIME_WAIT 会被误判成
"端口被占用"，表现为"刚退出再打开 App 必定启动失败"。

路径靠注入环境变量重定向到 App 私有目录，**必须在任何业务模块被导入之前设置** ——
路径常量是模块级求值的，晚了就不生效。

### 13.3 与桌面共用的部分

HTTP、WebSocket、推送、看门狗、TLS、页面渲染、全部业务逻辑**都是同一份代码**，
所以桌面上的改动会自动跟着走进 APK —— **前提是重新构建**。

⚠️ 数据在两台设备上**各自独立、互不同步**：共用的是同一套软件，不是同一份数据。

### 13.4 容器相关的坑（都踩过）

只在改安卓容器时需要，但每一条都很难从症状反推：

- **没有"直接执行 JS"的接口**：执行脚本的唯一入口是加载 `javascript:` 地址；
  会话对象上也没有"当前 URL"属性，得自己记。
- **证书错误没有服务端回调**：只有加载失败通知，而且**拒绝它也没用** ——
  放行只能靠**错误页里的页面内 JS** 自己去添加例外。
  ⚠️ 例外按 `主机:端口` 记，主站端口放行**不覆盖** WS 端口，两个都要放行一次。
- **错误页必须是 `data:` URL**：返回容器的内置错误页地址**不会让任何错误页加载**，
  只会白屏 —— 要自己造一个 `data:` 页面。
- **不能在"加载失败"那一拍执行放行**：那时文档还是空的，脚本会**静默失效**。
- **扩展用 manifest v2**：v3 会让扩展装不上（回调永远不来）。
- **基础库的默认请求头会泄露运行时与库版本**，建服务时要覆写掉。
- **主机名解析在安卓上注定失败**（主机名是机型名），相关逻辑要能跳过它；
  网卡名也不可信（热点网卡未必是 `wlan0`），**要用系统 API 区分 WiFi 与热点**。
- **重启 App 会重新解包内置资源** ⇒ 往解包目录里推文件**撑不过下一次启动**，
  不能用它做验证。

### 13.5 安卓侧的网络可达性

有一类问题只在安卓上出现：**访客访问用的地址，服务端自己认不出来**。
WiFi 与热点是两个不同网卡，而"默认路由出口地址"在开热点时往往指向蜂窝网络 ——
那个地址局域网里根本打不开。

所以：

- 提供一个"**收集本机全部地址**"的可替换钩子，安卓侧注册基于系统 API 的实现 ——
  这是唯一能拿到热点网卡地址的路子；
- "**唯一对外地址**"（二维码、分享链接、管理页显示）与"**全部本机地址**"（白名单、证书 SAN）
  是两个不同的东西，**不要合并**。前者错一个别人打不开，后者漏一个会把合法连接拒掉；
- 收集结果有**短 TTL 缓存** —— 它会被**每次 WS 握手**调用，而那里是同步回调
  （不能 await、也挪不进线程池），安卓上还要付 DNS 超时。代价是换网后最多延迟几秒反映。

## 14. 数据、日志与运行

### 14.1 目录布局

程序启动时派生五个目录，**全部落在"数据根"之下**（数据根按运行形态决定，见第 1.2 节）：

| 目录 / 文件 | 内容 |
|---|---|
| `config/` | 全部配置与数据文件（第 9.2 节的表） |
| `shared_files/` | 共享根：公共目录与各账号目录 |
| `shared_files/.uploads/` | **上传临时目录**（对用户不可见，见第 7.4 节） |
| `.cache/` | 运行缓存：缩略图、目录大小缓存、下载器会话文件等 |
| 日志文件 | 运行日志（滚动，见 14.3） |

**内置资源**（页面文件、随包的外部程序）与数据分开：前者在"资源根"（源码运行时是包目录，
打包运行时是解包目录），**只读**；后者在数据根，**可写**。这条区分是"打包后仍能运行"的关键。

⚠️ 上传临时目录**刻意放在共享根之下**而不是缓存目录：落位用的是"同盘原子替换"，
必须与目标同盘；而且这样它对配额口径的影响与原来一致。

### 14.2 运行缓存目录，与开发工作区

`.cache/` 是**服务的运行缓存**：缩略图、目录大小缓存、下载器的会话文件与节点缓存、
tracker 列表。它是运行产物（见 14.1 的表），服务自己建、自己用。

⚠️ 开发期的工作文件**不在这里**，它们住在项目根的 `.work/`：交接文档、探针脚本与输出、
截图、素材。那是开发者的工作区，在 `.gitignore` 里、不入库，服务一行代码都不碰它。

历史：2026-09-22 之前两者挤在 `.cache/` 一个目录里，于是"清理缓存"随时可能删掉工作文件。
分家时搬走的是**工作文件**，不是服务的目录 —— `.cache/` 是运行产物，给它改名会让所有已部署
的实例跟着迁移一次，而真正的问题（工作文件占了服务的地盘）一点没解决。

⚠️ 本文档 2026-09-22 之前写下的 `.cache/xxx` 路径（探针脚本、交接文档等）现在都在
`.work/xxx` 下；那些是当时的留痕，没有逐条改写，按这条换算即可。

清理 `.cache/` 时**不要用通配符批量删** —— 里面有下载器的会话文件，删了会丢断点续传状态。

### 14.3 日志

- **脱敏在唯一入口做**，不靠调用方自觉。用户可控的文本进日志的入口有一堆
  （请求行、用户名、异常详情……），靠"每个调用方都记得先处理"是防不住的 —— 已经漏过一次。
  入口会剔除换行与控制字符（换行注入能伪造日志行，控制字符会搅乱终端显示）；
- **短字段截断、长文本不截断**：异常堆栈截了就把线索丢了；
- ⚠️ **异常细节绝不回显给客户端**。Windows 的 `OSError` 文本**自带完整绝对路径**，
  黑盒渗透测试正是靠它把服务器目录布局还原出来的。做法是"对外固定文案、细节只进日志"，
  而不是在响应里做路径清洗；
- 查询串里的敏感参数（会话、令牌、口令、分享码）在访问日志里**打码**；
- 日志的**查看与清空有角色门禁**（管理员以上）。

### 14.4 看门狗

一个后台线程，每秒醒一次，判断"是否疑似卡死"：
**有请求在途（或 WS 近期活跃）且连续一段时间没有任何请求/消息完成**。

触发时把**全部线程的调用栈**写进一个带时间戳的证据文件，文件开头写明现场数据
（在途请求数、静默时长、时间），便于人工判断是误报还是真卡死。

- 判据里带**冷却时间**，避免同一个卡死现场被反复 dump；
- 长流下载期间没有其它请求时**可能误报一次** —— 文件头写明现场就是为了让人能判断；
- 开销可忽略（一个线程每秒醒一次）。

另有一条**手动通道**：设了环境变量后，运行时按 `Ctrl+Break` 可以随时把全线程栈写入文件。
两条通道互相独立。

### 14.5 内置外部程序

随包携带几个外部程序（证书生成、下载器、缩略图）。定位顺序是：
**打包解包根 → 主程序所在目录 → 源码资源目录 → 系统 PATH**，找不到返回"没有"，
由调用方降级 —— 例如缩略图生成失败会记一条日志（含返回码与错误输出尾部），
而不是静默假装"正在生成中"。

⚠️ **缺失不是错误**：源码运行时这些程序默认不入库，缺了只有相应功能不可用，其余照常。
README 里对用户是这么说的，代码里也是这么降级的。

## 15. 静态资源与缓存

### 15.1 默认不缓存，缓存是例外

缓存策略走**统一出口**：没有显式声明缓存策略的响应，会被兜底补成 `no-store`。
规则是"**默认不缓存，要缓存必须显式声明**"。

这条规则是被"漏"出来的：原先各处手写响应头，**一个都没发缓存头**的路径恰好包括最不该被
缓存的几个 —— 带授权凭据的成功响应、一次性二维码、用户文件内容与打包下载、公开分享页。
一刀切 `no-store` 也不行（静态资源会被反复全量重传），所以规则才定成"默认关、要开显式开"。

目前显式声明缓存的**只有两处**：静态资源与缩略图。

⚠️ 与之配套的一条：响应头里的"缓存策略已声明"标记是**统一出口用来判断要不要兜底的**。
写 304 响应时**必须显式再发一次缓存策略** —— 省了它，兜底逻辑就会把静态资源标成完全不可缓存
（因为它只看"这一条响应有没有声明过"）。有回归测试盯着这条。

### 15.2 条件请求

静态资源支持条件请求：响应带 `ETag` 与 `Last-Modified`，客户端下次带着验证器来，
**资源没变就只回响应头**（不传正文）。

判定的优先序与细节（都按 HTTP 规范）：

- **`If-None-Match` 存在时不再看 `If-Modified-Since`** —— 否则一个陈旧的后者会把前者的判定推翻；
- ETag 用**弱比较**，`W/` 前缀剥掉后比；
- 支持 `*`；
- 时间比较按 **UTC** 解释；真收到不带时区的日期也按 UTC 处理 ——
  落到系统本地时区会让判定整体偏移。

⚠️ 拿不到文件状态时**宁可不发验证器**（退回"每次全量"），也不要假装有一个 ETag。

### 15.3 为什么只有静态资源能这么做

`no-cache` 的语义是"**可以**存、但每次用之前必须回源验证"，而验证需要验证器。
以前一个验证器都没发，于是每次都回完整的 200 加整个文件 —— `no-cache` 实际退化成了
`no-store`，**省带宽的意图完全没兑现**。

⚠️ **安全前提**：静态资源发的是**原文件、不做任何替换** ⇒ 同一个 URL 对所有用户内容完全相同，
所以"没变就回 304"不会串味。

**按会话注入的页面是另一条路**：它们因人而异、始终是 `no-store`，
**不要顺手也给它们加验证器** —— 那会把某个用户的页面发给另一个用户。
测试里专门有一条钉住"匿名与已登录拿到同一个 ETag"。

## 16. 开发约定

### 16.1 注释

代码注释统一**中英双语**（一行中文说明 + 相邻一行英文，或同句双语），只留有信息量的注释，
删掉重复代码与过时/无意义的注释；英文部分可标注 AI 翻译。全库正在按此规范分批清理。

⚠️ 比"双语"更重要的是**注释要写"为什么"**。这个项目里最有价值的注释都是这一类：
"这样写，是因为曾经那样写出过什么问题"。**删代码前先读注释** —— 很多约束只存在于注释里，
代码本身看不出来。

### 16.2 测试

- 用 pytest，`tests/` 下按主题分文件；
- 大量测试**启动真实服务**（子进程 + 独立数据根 + 独立端口）而不是 mock ——
  测的是真实行为，代价是端口要预先分配、跑得慢一些；
- ⚠️ **"测试进程"与"测试用的数据根"是两回事**：直接在测试进程里调业务函数时，
  模块级路径常量指向的是**真实项目目录**。涉及落盘的白盒测试必须把文件路径
  monkeypatch 到临时根，否则会污染真实数据；
- **临时数据根"谁造谁登记"**，模块结束统一清理；长期残留由一条按"岁数"扫描的清理兜底；
- ⚠️ **先写测试、在未修代码上看它红**。这个项目不止一次靠这一步发现"测试其实没测到东西" ——
  **全绿不代表能测出缺陷，必须先确认它会红**；
- 改动共享状态的用例，**恢复要放 `finally`**：否则一条断言失败会留下脏状态，
  把后面一批用例一起带红，让人分不清"真失败"与"次生失败"；
- ⚠️ **静态断言型的测试要跟重构一起改**：它断言的是"代码里有没有这句话"，
  改了实现却没改它，全量测试会红 —— 这是好事，但要知道原因。

### 16.3 提交

- **一件一提交**：一个提交只做一件事；
- 提交信息写进文件再用 `-F` 传入（避开 shell 引号问题）。信息里写清
  **背景 / 根因 / 改法 / 验证**，以及**仍未动的地方**；
- 提交前用 `git diff --stat` 确认只动了预期文件；
- ⚠️ **不要把半成品提交进去** —— 未完成的东西会让人以为功能已经可用。

### 16.5 动手前的检查清单

改这个项目之前，值得先问自己几句：

1. **这件事有几条路？** 本项目最常见的缺陷类型是"同一个算法两份实现" ——
   目录列表、撤销会话、解锁判定都栽过。动手前先找到收口点，**改收口点，不要在别处补一份**；
2. **这个值会被谁读？** 加出口或读取点时，先看有没有现成的判定函数（第 2.1 节），
   调用它而不是再写一个条件；
3. **失败时会怎样？** 静默失败是本项目的重点清理对象：读配置出错被当成"不限"、
   删除失败被报成成功、缩略图失败与"正在生成"表现完全一样 ——
   **宁可报错，不要假装成功**；
4. **这个上限会不会把服务锁死？** 有些参数设小了会让服务无法自我修复
   （例如连接总数上限小到连"改回来"的请求都进不来）；
5. **改完怎么验证它真的生效？** 而且要**先确认这个验证手段能测出问题** ——
   本项目有过两次"验证通过"其实是验证方法本身无效（探针放错了页面、协议不匹配）。
